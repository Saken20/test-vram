# vramtest

[English](README.md) | Русский

**Сколько видеопамяти на самом деле нужно вашим инференс-сервисам и при какой нагрузке они ломаются?**

`vramtest` — нагрузочный тест для инференс-сервисов на GPU: LLM, распознавания речи, синтеза речи,
эмбеддингов или любого собственного HTTP / gRPC сервера с моделью. Он подаёт реалистичную нагрузку
(на отдельные сервисы или на целые многошаговые цепочки вроде ASR → LLM → TTS), десять раз в секунду
снимает VRAM GPU-процессов каждого сервиса, читает Prometheus-метрики vLLM и строит отчёт: сколько памяти
нужно каждому сервису для заданного числа пользователей, перцентили задержек, на какой параллельности
каждый сервис упирается в предел и сколько серверов нужно для целевой нагрузки.

Всё настраивается одним YAML-файлом: любое число сервисов, любые имена, любые модели.

## Зачем: nvidia-smi не показывает, сколько нужно модели в vLLM

vLLM при старте забирает `--gpu-memory-utilization × память GPU` и почти всё, что остаётся сверх весов
модели, отдаёт под **пул KV-кэша**. Поэтому `nvidia-smi` показывает одну и ту же большую цифру и на холостом
ходу, и под полной нагрузкой. Эта цифра говорит, сколько памяти вы *отдали* vLLM, а не сколько *использует*
ваша нагрузка. По ней нельзя понять, поместятся ли две модели на одну карту, насколько можно снизить
`--gpu-memory-utilization` и сколько одновременных пользователей выдержит сервер.

`vramtest` раскладывает эту цифру на части:

```
занято (NVML)   =  память модели (веса, CUDA-графы, активации)  +  KV-пул (зарезервирован, в основном пустой)
реально нужно   =  память модели  +  KV-кэш, занятый в пике нагрузки × (1 + запас)
```

и измеряет занятую часть под той нагрузкой, которую вы задали. Для сервисов, которые не резервируют память
заранее (большинство TTS-серверов, собственные сервисы на PyTorch), пиковая VRAM по NVML и есть их реальное
потребление — так она и попадает в отчёт.

## Возможности

- **Адаптеры**: OpenAI-совместимый API (chat, completions, transcription, speech, embeddings: vLLM, SGLang,
  llama.cpp server, Kokoro-FastAPI, ...), любой **gRPC**-метод из `.proto`-файла, который компилируется
  на лету (unary, серверный, клиентский и двунаправленный стриминг, аудио кусками), и любой **HTTP**-эндпоинт
  с JSON или multipart.
- **Цепочки (pipeline)**: одна реплика пользователя может пройти через несколько сервисов (например,
  аудио → ASR → LLM → TTS) с задержкой каждого шага, временем до первого токена/чанка и «ожиданием первого
  ответа» с точки зрения пользователя.
- **Сценарии**: холостой ход, одновременные залпы, непрерывная параллельная нагрузка, реалистичные сессии с
  паузами и ramp — рост параллельности до насыщения сервиса (ошибки, падение или превышение порогов задержки)
  с уточнением предела делением пополам.
- **Модель памяти** для vLLM: базовая память и KV-пул по отдельности, байт KV на токен из `config.json`
  модели, занятый KV из `/metrics`, prefix caching общего системного промпта, нижняя граница `max_model_len`.
- **Расчёт на нагрузку** для ваших целей («1000 одновременных пользователей»): сколько нужно памяти и серверов —
  по памяти и по производительности.
- **Отчёты**: сырые JSON по каждому сценарию, `report.md` + `report.json` и PDF-сводка понятным языком.
- **Поиск процессов**: GPU-процессы каждого сервиса находятся по его порту (Linux `/proc`), поэтому разные
  сервисы на одной GPU измеряются раздельно.
- Работает и без GPU (только нагрузка и задержки), а тесты гоняются на мок-серверах без GPU.

## Установка

Python 3.10+ на Linux с драйвером NVIDIA (NVML). Ставьте рядом с сервисами, в отдельное окружение, чтобы
не задеть окружения самих сервисов.

```bash
git clone https://github.com/Saken20/test-vram && cd test-vram

# pip + venv
python3 -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt

# или conda
conda env create -f environment.yml && conda activate vramtest
```

Необязательно: `pip install transformers` — точный подсчёт токенов токенайзером модели (см. `tokenizer`).
Обновление после `git pull`: `pip install -r requirements.txt` или `conda env update -f environment.yml --prune`.

## Быстрый старт

```bash
cp examples/vllm-chat.yaml config.yaml     # возьмите самый близкий к вашему случаю пример и поправьте
python -m vramtest validate                # разобрать конфиг, показать сервисы и цепочку
python -m vramtest probe                   # по одному запросу в сервис; GPU-процессы, vLLM /metrics, байт KV на токен
python -m vramtest all                     # idle, burst, concurrency, sessions, ramp, report, pdf
#   --quick       короткие длительности — сначала убедиться, что всё работает
#   --skip-ramp   без ramp (он давит сервисы до отказа и может уронить какой-нибудь)
python -m vramtest report                  # (пере)собрать results/default/report.md + report.json
python -m vramtest pdf                     # results/default/summary.pdf
```

Примеры:

| файл | что показывает |
|---|---|
| [`examples/vllm-chat.yaml`](examples/vllm-chat.yaml) | одна чат-модель в vLLM (Qwen/Qwen2.5-7B-Instruct), расчёт в пользователях |
| [`examples/voice-pipeline.yaml`](examples/voice-pipeline.yaml) | ASR → LLM → TTS: Whisper в vLLM, чат-модель в vLLM, Kokoro-FastAPI; голосовые сессии с паузами |
| [`examples/grpc-service.yaml`](examples/grpc-service.yaml) | свой gRPC-сервис по [`examples/protos/echo.proto`](examples/protos/echo.proto): unary, серверный стриминг, аудио клиентским стримом |
| [`examples/http-service.yaml`](examples/http-service.yaml) | свои JSON HTTP-эндпоинты (TGI `/generate`, TEI `/embed`), multipart — в комментариях |

### Попробовать без GPU

Мок-серверы из тестов можно запустить вручную:

```bash
python -m tests.mocks.openai_mock 8000      # OpenAI-совместимый сервер с /metrics в стиле vLLM
python -m vramtest --config examples/vllm-chat.yaml --quick --run demo all

python -m tests.mocks.grpc_mock 50051       # examples/protos/echo.proto
python -m vramtest --config examples/grpc-service.yaml --quick --run demo-grpc burst
```

Без NVML инструмент предупреждает, что VRAM не измеряется, но нагрузку и задержки записывает.

## Команды

```
python -m vramtest [--config ПУТЬ] [--run ИМЯ] [--quick] <команда> [опции]
```

| команда | что делает |
|---|---|
| `validate` | разбирает конфиг, компилирует `.proto`, загружает датасет; печатает сервисы и цепочку. Код выхода 2 при ошибках конфига, 1 при прочих проблемах |
| `probe` | по одному запросу в каждый сервис и одна реплика по цепочке; найденные GPU-процессы, vLLM `/metrics`, байт KV на токен. Пишет `probe.json` |
| `gen-audio [--service ИМЯ]` | озвучивает фразы датасета в `dataset.audio_dir/*.wav` сервисом, который умеет синтез речи (по умолчанию — первым найденным) |
| `idle` | VRAM без запросов |
| `burst [--levels 1,10,100] [--rounds N] [--service ИМЯ]` | N реплик, начатых в один и тот же момент |
| `concurrency [--users N] [--duration S] [--service ИМЯ]` | N воркеров шлют реплики одну за другой без пауз |
| `sessions [--profile ИМЯ\|all] [--duration S]` | K одновременных сессий с паузами; профили из конфига (по умолчанию все) |
| `ramp [--service ИМЯ\|pipeline\|all] [--levels ...] [--step S]` | наращивает параллельность до насыщения (по умолчанию — каждый сервис отдельно) |
| `report` | `results/<run>/report.md` + `report.json` |
| `pdf` | `results/<run>/summary.pdf` (сначала собирает отчёт) |
| `all [--skip-ramp]` | idle, burst, concurrency, sessions (все профили), ramp (каждый сервис), report, pdf |

- `--config ПУТЬ`: YAML-конфиг, по умолчанию `./config.yaml`.
- `--run ИМЯ`: результаты складываются в `results/<ИМЯ>/` в текущей папке (по умолчанию `default`). Удобно
  заводить отдельный прогон на каждую конфигурацию, например чтобы сравнить два значения
  `--gpu-memory-utilization`.
- `--quick`: idle 10 с, один залп на уровень, concurrency/sessions по 40 с, шаги ramp по 15 с без уточнения.
- `--service` для `burst` / `concurrency`: имя сервиса или `pipeline`. По умолчанию нагружается цепочка, если
  она задана, иначе каждый сервис по отдельности.
- Общие флаги можно писать и до, и после команды.

## Справочник по конфигу

В конфиге шесть разделов: `gpu`, `services`, `pipeline`, `dataset`, `scenarios`, `capacity`. Обязателен только
`services`, у остального есть значения по умолчанию. Относительные пути ищутся в текущей папке, затем рядом с
файлом конфига, затем в корне репозитория. На неизвестные ключи выводится предупреждение.

### `gpu`

```yaml
gpu: {index: 0, sample_hz: 10, metrics_poll_s: 1.0}   # индекс GPU в NVML, замеров VRAM в секунду, период опроса vLLM /metrics
```

### `services`

Любое число сервисов с любыми именами (буквы, цифры, `_`, `-`, `.`). Ключи, общие для всех адаптеров:

| ключ | по умолчанию | смысл |
|---|---|---|
| `adapter` | обязателен | `openai`, `grpc` или `http` |
| `model` | `""` | имя модели в запросах (openai: пусто = первый id из `GET /v1/models`); также плейсхолдер `{model}` |
| `request` | `{}` | openai: поля, добавляемые в тело запроса; grpc: шаблон сообщения-запроса |
| `timeout_s` | `120` | таймаут одного вызова |
| `limits` | `{max_p95_latency_s: 20, max_p95_ttfb_s: 3}` | ramp считает сервис насыщенным, если p95 выше этих значений |
| `port` | из `url`/`address` | порт, по которому ищутся процессы сервиса |
| `pids` | `[]` | явные PID GPU-процессов (вместо автопоиска) |
| `cmdline_match` | `""` | подстрока командной строки GPU-процесса (например, для сервисов в Docker) |
| `engine` | `vllm` для openai (кроме `speech`), иначе `generic` | `vllm` включает модель памяти с учётом KV-кэша |
| `metrics_url` | авто | Prometheus-эндпоинт vLLM; авто: `{url}/metrics`, затем порты, которые слушают процессы сервиса |
| `model_config` | `""` | id репозитория HF (`org/name`), локальный `config.json` или папка модели → байт KV на токен |
| `kv_bytes_per_token` | `null` | явный размер KV на токен (важнее `model_config`) |
| `kv_cache_dtype` | `null` | например `fp8`, если vLLM запущен с `--kv-cache-dtype fp8` |
| `weights_gib` | `null` | из строки лога vLLM `Model loading took X GiB` (иначе — размер `*.safetensors` в локальной папке `model_config`) |
| `kv_pool_tokens` | `null` | из строки лога vLLM `GPU KV cache size: N tokens`, если `/metrics` недоступен |
| `overhead_gib` | `1.0` | CUDA-графы / активации, добавляемые к `weights_gib`, когда базовую память не удаётся измерить |
| `max_model_len` | `null` | ваш `--max-model-len`: KV-пул не может быть меньше одной последовательности максимальной длины |
| `prefix_caching` | `true` | общий системный промпт занимает KV-кэш один раз, а не в каждом запросе |
| `tokenizer` | `""` | id/путь токенайзера HF для точного подсчёта токенов (нужен `transformers`) |
| `chars_per_token` | `4.0` | оценка числа токенов, если в ответе нет `usage` и токенайзер не задан |
| `audio_tokens_per_s` | `0` | KV-токенов на секунду входного аудио (ASR в стиле аудио-LLM) |
| `audio_out` | `{format: s16le, sample_rate: 24000}` | формат аудио, которое возвращает сервис: `s16le`, `f32le`, `pcm` (= s16le), `wav` или сжатые `mp3`/`opus`/`aac`/`flac` (без длительности) |

#### `adapter: openai`

```yaml
llm:
  adapter: openai
  url: http://localhost:8000        # корень сервера (можно и с /v1 на конце)
  kind: chat                        # chat | completions | transcription | speech | embeddings
  model: Qwen/Qwen2.5-7B-Instruct
  request: {max_tokens: 256, temperature: 0.7}
```

| kind | эндпоинт | вход | замер времени |
|---|---|---|---|
| `chat` | `POST /v1/chat/completions` | сообщения чата | SSE-стрим с `stream_options.include_usage`; TTFB = первый токен |
| `completions` | `POST /v1/completions` | текст | так же |
| `transcription` | `POST /v1/audio/transcriptions` | аудио, загружается WAV-файлом (multipart) | весь ответ; `request: {stream: true}` — потоковое распознавание vLLM |
| `speech` | `POST /v1/audio/speech` | текст | аудио приходит потоком; TTFB = первый чанк |
| `embeddings` | `POST /v1/embeddings` | текст | весь ответ |

`request: {stream: false}` отключает стриминг для chat/completions. Число токенов берётся из `usage` в ответе,
если он есть.

#### `adapter: grpc`

```yaml
asr:
  adapter: grpc
  address: localhost:50051
  proto: examples/protos/echo.proto     # + include_dirs: [...] для import
  method: echo.Echo/ClientStream        # "<package>.<Service>/<Method>"; тип стриминга берётся из .proto
  request: {meta: {id: "{uuid}"}}       # шаблон -> protobuf-сообщение (JSON-представление); список = несколько сообщений
  stream_audio: {field: chunk, chunk_bytes: 16000, realtime: true}
  response: {text: reply, audio: audio, ok: ok}
  metadata: {authorization: "Bearer <token>"}
```

- `.proto` компилируется на лету через `grpcio-tools` в кэш `vramtest/_gen/`.
- `stream_audio` (методы с клиентским стримингом): аудио реплики режется на сообщения по `chunk_bytes`; каждое —
  шаблон запроса с куском аудио в поле `field`. `realtime: true` отправляет куски со скоростью звука, как живой
  микрофон. Задержка считается с момента отправки последнего куска.
- `response`: пути к полям через точку. `text` и `audio` склеиваются по всем сообщениям серверного стрима;
  ложное значение поля `ok` помечает вызов как неудачный (`STATUS_FALSE`). TTFB = первое сообщение стрима.

#### `adapter: http`

```yaml
generate:
  adapter: http
  url: http://localhost:8080/generate
  method: POST                          # GET | POST | PUT | PATCH
  json: {inputs: "{text}", parameters: {max_new_tokens: 128}}
  # multipart: {file: "{audio_wav}", response_format: json}   # вместо json; байтовые значения уходят файлами
  headers: {Authorization: "Bearer <token>"}
  stream: false                         # true: читать тело кусками, TTFB = первый кусок
  response: {text: generated_text}      # путь в JSON через точку ("choices.0.text"); "$body" = всё тело
```

`response.audio` — это `"$body"` (сырые байты аудио) или JSON-поле с аудио в base64; `response.ok` работает
так же, как в gRPC.

#### Шаблоны и плейсхолдеры

Шаблонами являются `request` (openai, grpc), `json`, `multipart`, `headers`, `url` (http) и `metadata` (grpc):

| плейсхолдер | значение |
|---|---|
| `{text}` | текст реплики (фраза, расшифровка клипа или текстовый выход предыдущего шага) |
| `{audio}` | сырые байты аудио в формате `dataset.audio_in` |
| `{audio_wav}` | то же аудио в виде 16-битного WAV-файла |
| `{messages}` | сообщения чата `[{role, content}, ...]` (системный промпт + история + текст) |
| `{system_prompt}` | `dataset.system_prompt` |
| `{uuid}` | случайная hex-строка, новая на каждый вызов |
| `{session}` | номер сессии / воркера |
| `{model}` | `model` сервиса |

Значение, состоящее ровно из одного плейсхолдера, заменяется самим объектом (байты, список, число); иначе
плейсхолдеры подставляются в строку. Неизвестные `{имена}` и прочие фигурные скобки остаются как есть. Байты
аудио в `json`-теле http-запроса отправляются в base64. По плейсхолдерам же определяется естественный вход
сервиса, когда он нагружается отдельно: аудио, если он использует `{audio}`/`{audio_wav}`/`stream_audio`,
сообщения чата, если `{messages}`, иначе текст (openai: `chat` → сообщения, `transcription` → аудио,
остальные → текст).

### `pipeline`

Необязателен. Одна реплика проходит шаги по порядку:

```yaml
pipeline:
  - {service: asr, input: audio}
  - {service: llm, input: prev}
  - {service: tts, input: prev}
```

`input` — `audio`, `text`, `messages` или `prev` (выход предыдущего шага). Для чат-шага текст из `prev`
заменяет последнее сообщение пользователя, так что системный промпт и история сохраняются. Если шаг упал,
следующий шаг с `prev` получает исходный вход реплики, чтобы остальные сервисы всё равно получали нагрузку
(реплика при этом считается неудачной). Без цепочки `burst`, `concurrency` и `ramp` нагружают каждый сервис
отдельно его естественным входом (или тот, что указан в `--service`), а реплика в `sessions` вызывает каждый
сервис по одному разу.

### `dataset`

```yaml
dataset:
  texts: data/prompts.txt           # по фразе на строку ('#' = комментарий) или список прямо в конфиге
  audio_dir: data/audio             # WAV-клипы 16-bit PCM; <имя>.txt рядом с клипом = его расшифровка
  audio_in: {format: f32le, sample_rate: 16000}   # f32le | s16le: в каком виде {audio} уходит в сервисы
  system_prompt: ""                 # текст прямо здесь или путь к текстовому файлу
  history_turns: [0, 2]             # случайные предыдущие пары (пользователь, ассистент) в сообщениях чата
  seed: 0
```

Клипы пересэмплируются в `audio_in.sample_rate`. `gen-audio` заполняет `audio_dir` озвученными фразами
(`prompt_NN.wav` + `.txt`) любым сервисом, который возвращает аудио. Пока клипов нет, `probe` использует
синтетический тон длиной 1 с. В `sessions` история чата — это собственные предыдущие реплики сессии.

### `scenarios`

```yaml
scenarios:
  idle: {duration_s: 60}
  burst: {levels: [1, 10, 100], rounds: 3, pause_s: 3}
  concurrency: {users: 10, duration_s: 120}
  sessions:
    turns_per_session: 3
    session_duration_s: 30
    duration_s: 180
    profiles: {normal: 4, peak: 16}     # имя -> число одновременных сессий
    stagger_start: false                # false: все сессии начинают первую реплику в один и тот же момент
  ramp: {levels: [1, 2, 5, 10, 20, 40, 80, 160], step_duration_s: 60, max_error_rate: 0.05, bisect_steps: 2, cooldown_s: 5}
```

`sessions.stagger_start` (по умолчанию `false`): при `false` все сессии начинают первую реплику в один и тот же
момент — худший случай для первых секунд сценария; при `true` каждая сессия стартует в случайный момент в пределах
первых `session_duration_s`, и нагрузка распределяется так, как у независимых пользователей.

Подробнее — в разделе [Сценарии](#сценарии).

### `capacity`

```yaml
capacity:
  unit: session                         # слово для отчёта: user, session, stream, ...
  safety_margin: 0.10                   # запас поверх занятого KV-кэша
  targets:
    - {label: "1 session", sessions: 1}
    - {label: "peak (20 sessions)", sessions: 20}
    - {label: "500 concurrent sessions", sessions: 500}
```

`sessions` — число одновременно активных сессий (как в сценарии `sessions`), для которого отчёт
экстраполирует память и число серверов. Отчёт пишется по-английски, поэтому `unit` и `label` удобно задавать
по-английски.

## Модель памяти

Для каждого сервиса с `engine: vllm`:

1. **Байт KV на токен** — из `config.json` модели (`model_config`: id репозитория HF, скачивается один раз по
   HTTPS и кэшируется в `~/.cache/vramtest/`, либо локальный файл/папка):

   ```
   байт/токен = 2 (K и V) × num_hidden_layers × num_key_value_heads × head_dim × байт на элемент
   ```

   например, Qwen/Qwen2.5-7B-Instruct: 2 × 28 × 4 × 128 × 2 (bf16) = 57 344 байта = 56 КиБ на токен.
   Для моделей с MLA (как DeepSeek-V2/V3): `слои × (kv_lora_rank + qk_rope_head_dim) × байт на элемент`.
   В мультимодальных конфигах ищется текстовый декодер (`text_config`, ...). `kv_cache_dtype: fp8` вдвое
   уменьшает результат; `kv_bytes_per_token` его переопределяет. Для закрытых (gated) моделей нужен `HF_TOKEN`
   в окружении.
2. **Размер KV-пула** в токенах: из `/metrics` (`vllm:cache_config_info`: `num_gpu_blocks × block_size`),
   иначе `kv_pool_tokens` из строки лога vLLM `GPU KV cache size: N tokens`. Пул в ГиБ = токены × байт/токен.
3. **Базовая память** (веса, CUDA-графы, активации, CUDA-контекст) = VRAM процессов сервиса на холостом ходу −
   KV-пул. Если пул неизвестен: `weights_gib` (строка лога vLLM `Model loading took X GiB` или размер локальных
   safetensors) + `overhead_gib`.
4. **Занятый KV в пике**: `vllm:kv_cache_usage_perc` (`vllm:gpu_cache_usage_perc` в старых версиях) × пул.
   Без `/metrics`: токены запросов в работе (из `usage`, токенайзером или оценкой) × байт/токен; если есть и то,
   и другое, аналитика калибруется по `/metrics`.
5. **Prefix caching**: при `prefix_caching: true` общий системный промпт учитывается один раз, а не в каждом
   запросе.
6. **Нужно** = база + max(занятый KV, `max_model_len` × байт/токен) × (1 + `safety_margin`).

Для сервисов с `engine: generic` VRAM по NVML и есть их потребление; прирост на один запрос в работе
оценивается по сценариям.

**Экстраполяция.** По сценариям с сессиями отчёт берёт для каждого сервиса среднее число его запросов в работе
на одну активную сессию (*d*) и средний размер запроса в токенах. Для *N* сессий пик одновременных запросов
оценивается как `N·d + 3·√(N·d)` (пуассоновский поток, +3σ, не больше *N*), а от него — память. Предел из ramp
даёт ограничение по производительности; число серверов для цели — большее из «помещается в память»
(планируется не больше 95 % памяти GPU) и «укладывается в предел ramp». Сервис, чей GPU-процесс так и не был
найден, считается работающим на другой машине и в суммарную память не входит.

Откуда взято каждое число (`/metrics`, конфиг, значения из лога, оценка), указано в отчёте рядом с ним.

## Сценарии

**Реплика** — один проход по цепочке (или один вызов отдельного сервиса). Все сценарии записывают каждый вызов
(начало, начало обработки, первый токен/чанк, конец, код ответа, токены, секунды аудио) и всё время снимают
VRAM по процессам сервисов.

| сценарий | нагрузка | на что отвечает |
|---|---|---|
| `idle` | `duration_s` без запросов | память в покое: веса + зарезервированный пул |
| `burst` | N реплик, начатых в один момент, для каждого уровня, `rounds` раз | задержка, когда N пользователей договорили одновременно |
| `concurrency` | `users` воркеров, каждый шлёт реплики одну за другой | пропускная способность и память при постоянном числе запросов в работе |
| `sessions` | K сессий на профиль; каждая делает `turns_per_session` реплик за `session_duration_s`, затем начинается заново | реалистичная нагрузка с паузами; основа расчёта на нагрузку |
| `ramp` | уровни параллельности по `step_duration_s` каждый, пока уровень не провалится; затем `bisect_steps` делений пополам | где каждый сервис упирается в предел |

Уровень ramp проваливается, если доля ошибок выше `max_error_rate`, GPU-процесс сервиса завершился или p95
задержки / TTFB превысил `limits` сервиса. Ramp отдельного сервиса — это N воркеров без пауз (N = запросов в
работе); ramp `pipeline` — N одновременных сессий. Ramp ищет точку отказа: будьте готовы перезапустить сервис.

Задержка считается от момента, когда запрос полностью отправлен (для аудио клиентским стримом — после последнего
куска), до конца ответа; TTFB — до первого токена / чанка аудио / сообщения стрима. Для цепочки **ожидание
первого ответа** пользователем = сумма задержек всех шагов, кроме последнего, + TTFB последнего шага. Для аудио
RTF (real-time factor) = задержка / секунды аудио. У неудачных вызовов сохраняется код: `HTTP_503`, коды gRPC
вроде `RESOURCE_EXHAUSTED`, `TIMEOUT`, `CONNECT_ERROR`, `STATUS_FALSE`, ...

## Файлы результатов

Всё складывается в `results/<run>/` (по умолчанию `results/default/`):

| файл | содержимое |
|---|---|
| `probe.json` | результат `probe` |
| `idle.json`, `burst_<target>.json`, `concurrency_<target>_<users>.json`, `sessions_<profile>.json`, `ramp_<target>.json` | по файлу на запуск сценария: параметры, сведения о сервисах (PID, URL метрик, байт KV на токен), все вызовы, замеры VRAM, сводки по окнам |
| `report.md` | отчёт для чтения: память каждого сервиса в покое и в каждом сценарии, задержки, пределы ramp, расчёт на нагрузку |
| `report.json` | те же числа в машиночитаемом виде |
| `summary.pdf` | короткая сводка понятным языком для неспециалистов |

Повторный запуск сценария перезаписывает его файл; `report` читает все JSON, которые лежат в папке прогона.

## Ограничения

- Поиск процессов работает только на Linux (`/proc`), измерение VRAM — только на NVIDIA (NVML). Одна GPU на
  прогон (`gpu.index`); tensor parallel на несколько GPU не моделируется.
- Модель памяти с учётом KV-кэша — только для vLLM. Другие движки, которые тоже резервируют память заранее
  (TGI, SGLang, TensorRT-LLM, ...), измеряются как `generic`, то есть зарезервированная память считается занятой.
- `model_config` понимает конфиги decoder-only моделей (включая вложенные текстовые конфиги мультимодальных
  моделей и MLA), а также encoder-decoder моделей вроде Whisper (считается только KV self-attention декодера,
  KV cross-attention не учитывается); модели со скользящим окном
  внимания и гибридные (внимание + state-space) считаются как модели с полным вниманием.
- Без `usage` в ответах и без токенайзера число токенов — оценка (`chars_per_token`).
- Аудио между шагами (например, выход TTS → ASR) передаётся как есть, без конвертации формата. Входные WAV
  должны быть 16-bit PCM. У сжатого выходного аудио (mp3, opus, ...) нет длительности/RTF, и для `gen-audio`
  оно не подходит.
- Экстраполяция предполагает независимые сессии с измеренным поведением; по возможности проверяйте цель
  сценарием `sessions` на нужном уровне.
- Запросы к сервисам игнорируют `HTTP(S)_PROXY` (сервисы предполагаются локальными); только загрузка
  `config.json` с Hugging Face использует настройки прокси окружения.
- Для PDF нужен TrueType-шрифт, например DejaVu Sans (ищется в системных шрифтах, в conda-окружении и среди
  шрифтов, которые идут с matplotlib).
